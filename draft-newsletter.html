Lesson 2: The Cleanish Architecture

This series focuses on code organization and how it can set you and your AI up for success.

The first post, Lesson 1: Apps Over Layers, covered why organizing a monolith into feature-driven apps rather than flat technical layers keeps domains isolated, reduces blast radiuses, and sets up predictable boundaries for both humans and AI.

This post describes one way to structure what goes inside each app.

Fat Models and How Services Did Not Solve the Problem

In the early days of Django, the pattern we fell into was fat models and custom model managers. We were all focused on Model-View-Controller, but Django lacked an explicit controller, so logic ended up stuffed into models or views. That felt reasonable early on, but cross-model operations and abstractions quickly became cumbersome.

Attempting to fix this by introducing "service" or controller classes didn't solve the real problem. Taking logic out of models and views and putting it into services felt organized, but we still didn't have a clear framework for what kinds of work belonged where. What should the view stop doing? Where did database reads belong? We moved the code, but we didn't change the underlying confusion.

Flipping the Script on I/O

The typical approach when organizing code is to push the messy details down. An API endpoint calls a function, which calls a helper function, which calls another helper that finally executes a database query or calls a third-party API. This feels like abstraction: we go from high level to low level. In reality, it means every function we write performs I/O, which makes every single function hard to test because they all require mocks.

In his talk, The Clean Architecture in Python, Brandon Rhodes pointed out Uncle Bob's counter-intuitive insight: we need to flip the script and push I/O to the highest reasonable level.

Instead of having functions call other functions that perform I/O, use an orchestrator function: gather your data upfront, pass that data into your logic, and persist the results at the end. This means your logic functions pass around plain old data, making them easier to test. Testing the orchestrator function will require mocking, but it should only need a few tests.

Brandon Rhodes and Uncle Bob were not alone. Around the same time, Gary Bernhardt arrived at the same conclusion in his influential talk Boundaries, formalizing the idea with a descriptive name: "Functional Core, Imperative Shell." Where Brandon described pushing I/O up, Gary emphasized keeping the core pure: functions that perform no I/O and simply accept and return plain values are trivial to test, run fast, and avoid the slowdowns common in heavy integration suites.

The Power of Plain Data

This sounds simple and straightforward, but Brandon's later talk, his keynote at North Bay Python 2017, walks through building his terminal-based slide tool. Toward the conclusion of the talk, he admitted that even he—the person who gave the talk on Clean Architecture in Python—had failed to follow the pattern. He was stuck in the old ways.

His talk also reveals something even more powerful: preferring data over logic for flow control. Not only does his functional core pass back plain old data, but the data is complex and represents terminal state. The representation of state is cheap to edit, easy to assert in tests, and provides a robust debugging interface.

All that is needed is a relatively straightforward function that writes the final terminal state to the screen. The I/O is in the boundary.

Using data for control flow also ensures the orchestrator function is as simple as possible, avoiding branching code that would require additional mock-heavy tests.

The Clean(ish) Architecture

Uncle Bob’s full Clean Architecture attempts to abstract everything, even the framework itself. In ecosystems like Django or Rails, adopting that purist approach delivers diminishing returns. You end up writing domain entities, repositories, and data transfer objects for every single model, spending more time maintaining boilerplate than building features.

The approach I advocate—what I call the Cleanish Architecture—takes the core insights from Brandon and Gary without throwing away the conveniences of our frameworks. You do not need to create pure data doubles for every database model. If you squint, a Django model instance looks close enough to plain old data.

There are at least two caveats to making this work:

• Prefetch upfront: Ensure related data is loaded before it reaches your logic, so simple attribute access doesn't trigger a surprise database query.
• Treat models as read-only: Never call .save(), .update(), or mutating model methods inside your business logic. Saving state belongs strictly in your I/O functions.

Follow those two rules, and you get fast, mock-free tests without the enterprise ceremony.

Note: I have no problem letting unit tests hit the database in Django. The framework has always treated database-backed testing as a first-class citizen.

The One Rule: Easy To Change

In his talk One Rule to Rule Them All, The Pragmatic Programmer co-author Dave Thomas argued that every foundational design guideline—DRY, SOLID, decoupling, high cohesion—is just a special case of one single principle: ETC (Easy To Change). If an architectural pattern makes adapting to new requirements harder, it is a bad pattern.

This rule is fundamental because, as I always say:

You know the least at the beginning.

In fact, you always know less today than you will tomorrow. You are constantly discovering what the problem actually is, which means every architecture starts as an educated guess based on incomplete information. What ruins codebases isn't making imperfect guesses early on; it's the fear of changing them later when tests are slow, mocks are brittle, and code changes cascade in unexpected ways.

The Cleanish Architecture is simply about removing that fear. When you push I/O out of your business logic and into a shell, unit tests run fast without mocks, and refactoring stops being scary. You optimize for change because change is the only way your code adapts to what you learn.
